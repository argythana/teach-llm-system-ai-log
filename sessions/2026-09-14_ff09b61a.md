**Why the launcher, and not plain `uv run mlflow server`**

`mlflow server` is a command that starts a uvicorn subprocess and tells it to load one Python object: `mlflow.server.fastapi_app:app`. When the Assistant panel opens, that server asks `mlflow.assistant.providers.list_providers()` which providers exist. In MLflow 3.16 that function returns a list written in MLflow's source code: Claude Code, Codex CLI, the gateway, Ollama. There is no plugin hook, no entry point, and no configuration key that can add a provider. `~/.mlflow/assistant/config.json` can only *select* a provider that the server already has in memory, which is why the `copilot` entry there is ignored by a plain server, which then falls back to its default, Claude Code.

So a Copilot provider must be Python code running inside the server process. There were two ways to get it there. One is to change the environment itself: patch the installed MLflow package, or drop a `sitecustomize.py` into site-packages so every Python process registers the provider at startup. That is invisible, survives no reinstall, and the safety classifier refused it; I think rightly. The other is what I built: `llm_course/mlflow_app.py` registers the provider and then imports MLflow's own app, and `tools/mlflow_server.py` runs MLflow's real `server` command with one substitution, the app name handed to uvicorn. Same database, same flags, same UI, same everything else; the only difference is that the provider list is longer.

The consequence is exactly what you observed: run `tools/mlflow_server.py` and the panel shows "GitHub Copilot CLI", selected; run plain `mlflow server` and it does not. Students never need the launcher. If you want it to become unnecessary, the provider would have to be contributed to MLflow itself, which is a small pull request since it mirrors their Claude Code provider; I can prepare that when you wish.
