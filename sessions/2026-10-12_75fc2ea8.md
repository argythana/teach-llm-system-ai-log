**Claude:**

I'm checking in Ollama's API source what happens when the prompt or the answer reaches the end of the window. Then I'll answer.

There is only one window. Your prompt and the model's answer share it, and no separate input window or output window exists inside the model. The settings that look like an output window are caps that sit inside that one window.

**Why only one window**
The model writes by adding each new token to the end of the same sequence that holds your prompt. A generated token is stored in the window just like a prompt token. The model learned to handle a certain number of positions during training, so that number limits prompt and answer together.

**Settings in Ollama**

| Setting | What it controls |
|---|---|
| `num_ctx` | The total window for a call: prompt plus answer. Its maximum is the model's trained length. |
| `num_predict` | A cap on answer tokens. The default is `-1`, no cap: the model stops at its stop token or when the window is full. |
| *(no input setting)* | The prompt can use whatever the window leaves. |

`num_predict` lives inside `num_ctx`. With a 4096 window and a 3000-token prompt, the answer has about 1096 tokens left, whatever `num_predict` says.

When either part doesn't fit, Ollama has traditionally handled it quietly:
- **Prompt too long:** it cuts the start of the prompt, as the PELICAN example in the notebook shows.
- **Answer reaches the end of the window:** it drops early tokens so it can keep writing.

Ollama's current API source adds `truncate` and `shift` options to chat requests, which return an error instead. The Python client installed in this repo only offers `truncate`, and only for embeddings.

**How to find the numbers**
- **The model's maximum:** `ollama show qwen3:1.7b` prints `context length 40960`, and the Hugging Face `config.json` says `max_position_embeddings: 40960`.
- **What the model card says:** the [Qwen3-1.7B model card](https://huggingface.co/Qwen/Qwen3-1.7B) gives "Context Length: 32,768". The [Qwen3-8B card](https://huggingface.co/Qwen/Qwen3-8B) explains the gap: 40,960 "includes reserving 32,768 tokens for outputs and 8,192 tokens for typical prompts". That is a recommended split of one window, not two windows.
- **A number to ignore:** the tokenizer's `model_max_length` is 131072 here. It's a tokenizer setting, not the model's limit.
- **The window actually in use:** the `CONTEXT` column of `ollama ps`.
- **Usage per call:** `prompt_eval_count` + `eval_count` must fit in `num_ctx`. `done_reason == "length"` means the answer hit `num_predict`.

**Hosted models** are where you see two numbers. Providers publish a context window and a lower maximum output, and each request sets its own output cap, such as `max_tokens`. That maximum output is a rule the provider sets: they train and serve the model for answers up to that length, partly because long generations are slow and expensive. It still sits inside the same window, so input plus output must fit in it. A reasoning model's thinking tokens also count as output and use the window.
